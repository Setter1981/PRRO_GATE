## 1. Protocol of record

**Production DPS is gRPC over HTTP/2 + TLS.** Proto3.

Evidence:
- `src/prro_gateway/transports/proto/fiscal_server.proto:1-14` declares
  `syntax = "proto3"`, `package com.programika.rro.ws.chk`, and
  `service ChkIncomeService` with five RPCs.
- `src/prro_gateway/transports/dps_fiscal_server.py:1-9` documents the
  service header verbatim and points at `cabinet.tax.gov.ua/help/api.html`
  as the upstream contract source.
- `src/prro_gateway/transports/dps_fiscal_server.py:124,131,138`:
  `import grpc; grpc.ssl_channel_credentials(...); grpc.secure_channel(...)`
  — the live wire is unambiguously gRPC/TLS, not SOAP/XML-RPC/REST.
- `src/prro_gateway/transports/dps_fiscal_server.py:226-236`: the live
  call is `stub.sendChkV2(pb.Check(...), timeout=30.0)` against the
  generated `ChkIncomeServiceStub` from
  `transports/proto/fiscal_server_pb2_grpc.py:28-61`.
- Endpoints, named in code: production `prro.tax.gov.ua:443`
  (`dps_fiscal_server.py:151`), test `cabinet.tax.gov.ua:9443`
  (`dps_fiscal_server.py:7-8`).
- Project memory `Sprint 7 proven` records a full live SHIFT_OPEN →
  SELL → Z_REPORT cycle succeeded against
  `cabinet.tax.gov.ua:9443` — operationally confirms the gRPC contour.

The Python sidecar wrapper (`fiscal_sidecar.py`) is **not** an
alternative protocol — it is a thin httpx shim that POSTs canonical
JSON to a local Rust binary that itself talks gRPC to DPS
(`fiscal_sidecar.py:5-6`: "Rust sidecar owns: XML build → CMS sign
(DSTU 4145) → gRPC sendChkV2"). It does not represent a second wire
format that the prro Rust gateway must mock.

There is no SOAP, no XML-RPC, no REST in any production DPS code path
in the repo.

## 2. Schema artefact the W1+ mock generates from

**Canonical artefact:** `src/prro_gateway/transports/proto/fiscal_server.proto`
(SHA today: shipped at HEAD, not regenerated).

Recommended placement for W1+:

  `rust/prro/proto/fiscal_server.proto` at the start of M2-W1, and
  generate Rust bindings with `tonic-build` in a build.rs in
  `prro/build.rs` (or a dedicated `prro_proto` crate).
- `scripts/mock_dps.proto` and `scripts/mock_dps_server.py` may be
  retained as latency/jitter benchmarks (different concern), but they
  must not be confused with the contract mock.

## 3. Contract subset prro must mirror

The Rust `DpsChannel` (spec §8.1) interacts with five RPCs on
`com.programika.rro.ws.chk.ChkIncomeService`. All are unary
(`unary_unary` per `fiscal_server_pb2_grpc.py:37,42,47,52,57`); none
are streaming.

Mapping `DpsChannel` trait → wire RPCs (per
`docs/superpowers/specs/2026-04-22-rust-rewrite-design.md:763-770`
and `dps_fiscal_server.py`):

| `DpsChannel` op (spec §8.1) | gRPC RPC | Request type | Response type | Used by |
|---|---|---|---|---|
| `submit(DpsSubmission)` | `sendChkV2` | `Check` | `CheckResponse` | write-path send-stage; offline-codes T=112 piggybacks here (see §3.4) |
| `query_status(ByServerFiscalNo)` | `lastChk` | `CheckRequest` | `CheckResponse` | recovery (`dps_fiscal_server.py:262-349`) |
| `query_status(ByLocalIdentity)` | — | — | — | NOT supported by DPS today (see §3.5) |
| (capabilities probe — §3.6) | `ping` | `Check` | `CheckResponse` | health/liveness (`dps_fiscal_server.py:365-385`) |
| (ops probe — §3.6) | `statusRro` | `CheckRequest` | `StatusResponse` | per-FN status (`dps_fiscal_server.py:428-441`) |
| (ops probe — §3.6) | `infoRro` | `CheckRequest` | `RroInfoResponse` | per-FN registration metadata (`dps_fiscal_server.py:443-465`) |

### 3.1 `sendChkV2` — primary write-path RPC

Method name on the wire: `/com.programika.rro.ws.chk.ChkIncomeService/sendChkV2`
(`fiscal_server_pb2_grpc.py:38`).

Request `Check` (`fiscal_server.proto:16-30`):

| Field | Wire type | Source in `DpsSubmission` | Notes |
|---|---|---|---|
| `rro_fn` | string | `fiscal_number` | FN as decimal digits |
| `date_time` | int64 | `business_ts` (Kyiv-local-as-epoch) | `dps_fiscal_server.py:55-81`; tzdata-required |
| `check_sign` | bytes | `signed_cms` | CMS DER bytes; UTF-8 string fallback only on dev/passthrough crypto (`dps_fiscal_server.py:223`) |
| `local_number` | int32 | `local_number` (LND) | `0` for SHIFT_OPEN per DPS contract (`dps_fiscal_server.py:189-190`) |
| `check_type` | enum {`UNKNOWN`=0, `CHK`=1, `ZREPORT`=2, `SERVICECHK`=3} | `doc_type` mapped via `_OP_TO_CHECK_TYPE` (`dps_fiscal_server.py:101-109`) | SHIFT_OPEN→SERVICECHK, SELL/RETURN/SERVICE_*/CASH_WITHDRAWAL→CHK, Z_REPORT→ZREPORT |
| `id_offline` | string | `offline_fiscal_no` (stringified) | empty for online (`dps_fiscal_server.py:196`) |
| `id_cancel` | string | `cancellation_of` server fiscal id | empty unless cancellation/return (`dps_fiscal_server.py:193`) |

Response `CheckResponse` (`fiscal_server.proto:36-62`):

| Field | Wire type | Maps to `DpsResponse` |
|---|---|---|
| `id` | string | `DpsAck.server_fiscal_no` (`dps_fiscal_server.py:251-258`) |
| `status` | enum (see §3.3) | drives `Ack` / `Reject` / `NeedsReconciliation` / `Retryable` (`dps_fiscal_server.py:507-550`) |
| `id_sign` | bytes | DPS signature of `id` (archive-only) |
| `data_sign` | bytes | DPS signature of full payload (archive-only) |
| `error_message` | string | human-readable; required for hash extraction in MAC recovery (`dps_fiscal_server.py:494-504`) |

### 3.2 `lastChk` — recovery RPC (`ByServerFiscalNo` outcome)

Method on wire: `/com.programika.rro.ws.chk.ChkIncomeService/lastChk`
(`fiscal_server_pb2_grpc.py:43`).

Request `CheckRequest` (`fiscal_server.proto:32-34`): single field
`rro_fn_sign` (bytes) — a CMS-signed-raw signature over the FN
bytes, NOT the FN itself. The signature is produced by
`crypto_provider.sign_raw(fiscal_number.encode('utf-8'))`
(`dps_fiscal_server.py:296`). This means `query_status` is gated
on a working crypto provider (`dps_fiscal_server.py:287-293`).

Response is `CheckResponse` (same as `sendChkV2`).

Match rule for recovery (`dps_fiscal_server.py:332-349`):
`response.id == transport_request_id` ⇒ `Found(ack)`; otherwise
`Retryable`/`Ambiguous`. The Rust `DpsChannel::query_status`
(spec §8.5) classifies this into `DpsStatusOutcome::Found / NotFound /
Ambiguous`.

### 3.3 `CheckResponse.Status` enum — full table

From `fiscal_server.proto:38-57`. The mock MUST allow injecting any
of these values for negative-path tests; the prro write-path maps
them to typed errors (`dps_fiscal_server.py:560-577`,
`canonical_error_from_dps_status`):

| Status | Numeric | Class (Rust mapping per ADR-M2-2 + §5.5) |
|---|---|---|
| `UNKNOWN` | 0 | Retryable (`dps_fiscal_server.py:536-539` — proto-default treated as transport anomaly) |
| `OK` | 1 | Ack |
| `ERROR_VEREFY` | -1 | Reject (signature/crypto) |
| `ERROR_CHECK` | -2 | Reject (RRO verification) |
| `ERROR_SAVE` | -3 | Reject (write error / duplicate) |
| `ERROR_UNKNOWN` | -4 | Retryable with cooldown (project memory `DPS rate limit`: status=-4 ⇒ 5+ min cooldown) — see drift §5 |
| `ERROR_TYPE` | -5 | Reject |
| `ERROR_NOT_PREV_ZREPORT` | -6 | Reject |
| `ERROR_XML` | -7 | Reject |
| `ERROR_XML_DATE` | -8 | Reject |
| `ERROR_XML_CHK` | -9 | Reject |
| `ERROR_XML_ZREPORT` | -10 | Reject |
| `ERROR_OFFLINE_168` | -11 | Reject |
| `ERROR_BAD_HASH_PREV` | -12 | NeedsReconciliation (`DpsMacRecoveryError`, expected hash extracted from `error_message` via regex `dps_fiscal_server.py:494`) |
| `ERROR_NOT_REGISTERED_RRO` | -13 | Reject |
| `ERROR_NOT_REGISTERED_SIGNER` | -14 | Reject |
| `ERROR_NOT_OPEN_SHIFT` | -15 | Reject |
| `ERROR_OFFLINE_ID` | -16 | Retryable transient (`fiscal_sidecar.py:39` notes -16 = offline session expired ⇒ retry after reconnect) — see drift §5 |

The 16 distinct `ERROR_*` codes plus `OK` and `UNKNOWN` are the full
contract surface for response classification. Mock must expose all
18 values via test-knob (e.g. injectable by request idempotency-key
or by header).

### 3.4 Offline-code allocation (T=112) shares `sendChkV2`

`dps_fiscal_server.py:387-426` (`request_offline_codes`) sends a
`Check` with `check_type=SERVICECHK` and a CMS-signed T=112 XML
body, then reads `response.fns_data` to parse allocated FN integers.

**This field is NOT in the checked-in
`src/prro_gateway/transports/proto/fiscal_server.proto`.** The
generated `pb2.CheckResponse.DESCRIPTOR.fields` enumerates exactly
five fields (`id`, `status`, `id_sign`, `data_sign`, `error_message`)
— verified by introspection during this research. This is real
drift between code and the proto file in the repo (see §5).
Implication for the mock: until the production proto is reconciled,
the W1+ mock MUST mirror the **five-field** `CheckResponse` from the
checked-in proto; `request_offline_codes` is not in the M2-W1
critical path and can be deferred until §6 is closed.

### 3.5 `query_status(ByLocalIdentity)` is unsupported by DPS today

Spec §8.5 (`2026-04-22-rust-rewrite-design.md:824-860`) defines two
status-query shapes. `ByServerFiscalNo` maps to `lastChk`. **There
is no DPS RPC for `ByLocalIdentity`** (no by-content lookup over
canonical hash + LND in `ChkIncomeService`). The
`GrpcCabinetChannel::query_status` MUST therefore return
`DpsStatusOutcome::QueryNotSupported` for the `ByLocalIdentity`
variant, and recovery falls into the `RequiresManualReconciliation`
hard-block path per spec §8.5.

This is a known constraint of the gRPC contour, not a gap to fix in
M2. The mock MUST exercise `QueryNotSupported` for `ByLocalIdentity`.

### 3.6 Ops probes (`ping`, `statusRro`, `infoRro`)

These are **operator/admin** RPCs, not write-path. The M2 mock must
implement them at minimum to a "returns OK with deterministic
values" fidelity for admin-UI / health integration tests; full
fidelity is not required for write-path correctness.

- `ping` (`fiscal_server.proto:11`): same `Check` request/response
  shape as `sendChkV2` with `check_sign=b''`; expected to round-trip
  with `status=OK` (`dps_fiscal_server.py:365-385`). Used by node
  online-detection.
- `statusRro` (`fiscal_server.proto:12`): `CheckRequest` (signed FN)
  → `StatusResponse` with `open_shift`, `online`, `last_signer`,
  `status`, `error_message` (`fiscal_server.proto:64-79`).
- `infoRro` (`fiscal_server.proto:13`): `CheckRequest` →
  `RroInfoResponse` with full RRO registration metadata
  (`fiscal_server.proto:81-113`) — 16 fields including
  `offline_allowed`, `single_tax`, `tins`, `name`, `addr`, repeated
  `Operator`. The mock can return a fixed canned record per FN.

## 4. Transport-level behaviours the mock MUST cover

Derived from `dps_fiscal_server.py` (live transport) and ADR-M2-2
"Tests required":

### 4.1 Wire-level

- **TLS:** mock listens on TLS by default; cert may be self-signed for
  CI (Python bench mock already does this — `mock_dps_server.py:102-142`
  via `trustme` or `openssl`). Test client trusts the mock CA. The
  mock MUST also have an **insecure** mode for local fast iteration —
  prro's `_create_grpc_channel` passes
  `grpc.ssl_channel_credentials` always, so the mock must reflect
  the production posture.
- **HTTP/2 keepalive:** prod settings observed and codified at
  `dps_fiscal_server.py:132-138`:
  `grpc.keepalive_time_ms=30000`, `grpc.keepalive_timeout_ms=10000`,
  `grpc.keepalive_permit_without_calls=1`,
  `grpc.http2.max_pings_without_data=0`. Mock should accept these
  PING frames without disconnecting; a streaming/idle test (60-120 s
  hold) is desirable.
- **Deadlines:** prod call timeouts: `sendChkV2` = 30 s
  (`dps_fiscal_server.py:236`), `lastChk` = 15 s
  (`dps_fiscal_server.py:316`). Mock MUST be controllable to delay
  past those (deadline-exceeded test), and to honour `grpc-timeout`
  metadata.

### 4.2 Authentication / metadata

- **No application-level auth headers** in the prod transport — auth
  is via mTLS or the JKS-signed `check_sign` payload itself (the CMS
  signer's identity binds to a registered DPS signer; rejection
  surfaces as `ERROR_NOT_REGISTERED_SIGNER=-14`). The mock therefore
  does not need to validate `authorization` or any custom header,
  but MUST accept arbitrary metadata without rejecting (forward
  compatibility).
- **Idempotency:** there is **no client-side idempotency key on the
  wire**. Idempotency is per `(rro_fn, local_number)` — DPS
  deduplicates by these two fields plus `check_sign` content. The
  mock MUST reflect this: a re-`sendChkV2` with the same `(rro_fn,
  local_number)` should return the same `id` and `status=OK` (or a
  defined "duplicate" reject — observed `ERROR_SAVE=-3` per code
  comment `dps_fiscal_server.py:514`).

### 4.3 Error categorisation (per ADR-M2-2 "Tests required")

Mock MUST support injecting:

- **gRPC-level status** — `INVALID_ARGUMENT`, `UNAUTHENTICATED`,
  `DEADLINE_EXCEEDED`, `UNAVAILABLE`, `INTERNAL`. These are
  transport-level and currently caught by the generic `except
  Exception` (`dps_fiscal_server.py:241-242`) → `TransportRetryableError`.
  The Rust `DpsTransportError` MUST split these into typed variants;
  the mock MUST be able to emit each.
- **Mid-call connection drop** — server closes the stream after
  receiving the request but before sending the response. Tests for
  ambiguous-outcome path per spec §8.5.
- **Application-level `CheckResponse.Status<0`** — every value in
  §3.3, including the `UNKNOWN=0` "proto default" case
  (`dps_fiscal_server.py:533-539`).

### 4.4 Rate-limit shape

Project memory `DPS rate limit` records the live test host returns
`status=-4` (`ERROR_UNKNOWN`) after too many errors, with a 5+ min
cooldown. The mock SHOULD support a configurable
"after N failures emit -4 for T seconds" mode for cooldown tests.

### 4.5 Streaming

**None.** All five RPCs are unary (`fiscal_server_pb2_grpc.py:37-61`,
all use `unary_unary`). The mock does not need streaming server- or
client-side. Spec §8.1 (`design.md:765-770`) assumes
`async fn submit/query_status` returning a single value, consistent
with this.

### 4.6 Channel reuse & lazy init

Production keeps a per-endpoint stub cache (`dps_fiscal_server.py:351-362`).
The mock test rig MUST tolerate multiple concurrent stubs from a
single client process and not require pre-registration.

### 10.2 Public WebCheck TaxGrpc COM surface

`TaxGrpc/TaxGrpc/IClient.cs:7` exposes only `Open / Check(version) /
Ping / CheckLast`.  The destructive `delLast*` RPCs are
**generated-but-private** even in WebCheck — they live in the

contract.  WebCheck `Client.cs:57,114` routes `Check(1)` to

(`WebCheckMain/WebCheck/All.cs:20`).

### 10.3 M2 W3 scope decision

The 5 RPCs marked ✅ in §10.1 remain valid M2 W3 scope.  The 3
deferred RPCs are explicitly NOT in M2 W3 scope:

- **`sendChk` (API v1)** — deferred unless a pilot configuration
  hard-codes `apiver=1`.  Default WebCheck-era configs use v2, so
  new pilots can be configured for v2 from day one.  An auto-
  migrate-or-refuse decision for legacy `apiver=1` configs lands
  in PRRO_GATE-0ps before pilot scope review.

- **`delLastChk` / `delLastChkId`** — destructive / admin /
  recovery operations.  These MUST NOT fold into the normal
  `DpsChannel` casually.  Deferred to a separate
  "DpsAdminOps / manual recovery" ADR + design with:
    - typed admin-only API surface (e.g. a `DpsAdminChannel` trait
      separate from `DpsChannel`),
    - audit_log entry on every call,
    - hard gate (CLI flag / admin role / ops-only feature flag),
    - reconciliation rules with `services::write_path`.

This drift is tracked as **PRRO_GATE-0ps** (P1; child of
PRRO_GATE-82j M2 epic); the W3 sign-off gate references the
decision recorded there.
