## Headline finding (read this first)

**The "CMP" in this codebase is NOT RFC 4210 CMP.** Server-side path
naming is misleading. Every Ukrainian CSP exposes a folder called
`/services/cmp/`, but the bytes on the wire are an IIT-proprietary
120-byte binary lookup record wrapped in a PKCS#7 `id-data`
ContentInfo, reverse-engineered from `dstucrypt/agent`
(`jkurwa/lib/services/cmp.js`). See `rust/prro_crypto/src/cms/cmp.rs:1-56`
for the verbatim wire-format documentation in the existing crate.

Implications that ripple through the rest of this document:

- **Only one operation exists** in this protocol family: cert
  *lookup-by-SKI*. There is no enrolment, no rekey, no revocation, no
  status-poll over this channel — those happen out-of-band via the CA's
  web UI / paper procedure.
- **There is no auth on the request.** The 120-byte payload carries
  the SKI you want; no shared secret, no signed PKIMessage, no client
  cert. Tamper-resistance of the read-only lookup rests on TLS to the
  CA front (`http://...:80` is, per IIT convention, fronted by a TLS
  terminator that 301-redirects browsers but accepts plain HTTP POSTs
  on `/services/cmp/`).
- **`prro_crypto` already speaks this protocol natively.** M2 does NOT
  need to port any encoder/parser; `cert_refresher` is a thin wrapper
  around an existing function call.

This dramatically narrows W1+ scope vs. what ADR-M2-4's open-risk
language ("authentication mode … still spec-only", "implement a thin
`CmpClient`") implied.

## 1. CMP operations cert_refresher must perform

The ADR-M2-4 task list ("initial enrolment / re-key / refresh /
status-poll") presumed RFC 4210 semantics. With the IIT protocol on the
wire, the actual list collapses to **one operation, used three ways**:

| Logical use case | CMP operation needed | Implementation in Python |
|---|---|---|
| Initial enrolment (cert resolution at onboarding) | `cert lookup by SKI` | `services/cert_provisioning.py:218-300` (the CMP fallback path inside `provision_cert`) |
| Re-key / fresh CA-signed cert after key roll | `cert lookup by SKI` | NOT separately implemented in Python — re-key is handled by re-running onboarding after the operator rotates their JKS/ZS2 |
| Periodic refresh (cert nearing expiry) | `cert lookup by SKI` | `services/cert_provisioning.py:383-464` (`refresh_expiring_certs`) — iterates `operator_certs` rows whose `valid_to` is within `refresh_within_days`, calls the same CMP fetch |
| Status-poll (revocation / OCSP / CRL) | NOT this channel | OCSP/CRL fetch lives in `prro_crypto::cms::revocation` (`rust/prro_crypto/src/cms/revocation.rs:371,376,424`) under the same `tsp_http` feature; **not** in scope of `cert_refresher` per ADR-M2-4 |

**File-line cites for the single primitive used by all three flows:**
- Python entry-point that does the CMP call:
  `services/cert_provisioning.py:243` —
  `cmp_cert = fetch_fn(candidate_url, key_ski, effective_timeout)` where
  `fetch_fn = self._crypto.fetch_cert_by_ski`.
- Multi-URL retry policy (caller URL > registered CA endpoints by
  priority > legacy `cert_provisioning_config.primary_cmp_url`):
  `services/cert_provisioning.py:472-501`.
- Refresh schedule (background polling, outside any DB tx):
  `services/cert_provisioning.py:383-464`. Note the file's docstring
  at line 26-29 already calls out FI-1 compliance: "the CMP fetch in
  `provision_cert` completes before the short `BEGIN IMMEDIATE` that
  performs the upsert."

**The Rust primitive that the M2 `cert_refresher` will call:**
- `prro_crypto::cms::cmp::fetch_cert_by_ski(cmp_url: &str, ski: &[u8],
  timeout: Duration) -> Result<Vec<u8>, CmpError>` —
  `rust/prro_crypto/src/cms/cmp.rs:311-349`. Returns DER-encoded
  end-entity certificate bytes verified to match the queried SKI.
- Pyo3 wrapper of the same function (the one Python calls today):
  `rust/prro_crypto/src/python.rs:840-862,899`.
- Live tests against acskidd / privatbank / uakey are kept under
  `#[ignore]` on `#[cfg(feature = "tsp_http")]`:
  `rust/prro_crypto/src/cms/cmp.rs:516-590`. These prove the wire
  format works; **they MUST NOT run in CI** (acceptance criterion).

**Operations the schema mentions but no code implements:**

`operator_certs.source` enum is `('container','cmp','manual')`
(`rust/prro/migrations/003_operators_printers.sql:41`). All three
sources route writes through the same `upsert` repository call
(`src/prro_gateway/repositories/operator_certs.py:28-75`); the source
field is a *provenance label*, not a separate operation. This
trivially carries over to the Rust port — no extra CMP operations
needed.

## 2. Auth model (with cites)

**The cert lookup carries no authentication of any kind.** It is a
SKI-keyed read on a public CA endpoint.

Evidence:
1. The 120-byte wire payload has no auth fields. The full layout is
   documented at `rust/prro_crypto/src/cms/cmp.rs:14-28`:
   - byte 0: msg type (`0x0D` = cert lookup)
   - bytes 8-11: u32 LE = 2 (probably version)
   - bytes 12-43: primary 32-byte SKI
   - bytes 44-75: secondary SKI (a copy of primary in single-key
     lookups)
   - bytes 76-107: zero reserved
   - bytes 108, 112: flag bytes (0x01)
   - rest: zero reserved
   No nonce, no signature, no MAC, no shared secret.
2. The HTTP request, per `rust/prro_crypto/src/cms/cmp.rs:325-329`,
   sends only `Content-Type: application/octet-stream` and
   `Content-Length`. No `Authorization`, no client cert
   (`ureq::AgentBuilder::new()` at line 319 is built with default TLS
   only — no client identity).
3. The Python orchestrator confirms this trust model in its module
   docstring: `services/cert_provisioning.py:36-39` —
   > "We do NOT verify CMP response signatures. TLS/routing to the
   > Ukrainian CA front covers tamper-resistance for a read-only
   > lookup. Signed-CMP uplift is a later sprint if audit requires it."
4. The orchestrator does perform an *integrity check* on the response
   payload before persisting it: it recomputes the SKI of the returned
   cert and refuses to write if it does not match the queried SKI.
   This is at:
   - Python: `services/cert_provisioning.py:271-279` (initial fetch)
     and `services/cert_provisioning.py:441-449` (refresh path).
   - Rust (already inside `fetch_cert_by_ski`):
     `rust/prro_crypto/src/cms/cmp.rs:235-241` — the parser only
     returns a cert whose recomputed SKI matches the query, so the
     caller-side Python re-check is belt-and-braces but the Rust
     primitive enforces it.

**Implication for `cert_refresher` design:**

Because the channel is unauthenticated, the M2 `cert_refresher` does
NOT need:
- A `cred_salt`/`jks_password` unseal step before calling CMP (so
  ADR-M2-5 applies *only* to the signing path, not the cert-fetch
  path).
- Any operator-cert-as-bootstrap-credential logic (no chicken-and-egg
  problem at first enrolment).
- Any signed-PKIMessage encoder.

The only invariant that ADR-M2-5 preserves on this path is the
*response*-side SKI re-check before persistence (already enforced in
the Rust primitive, reinforce in the orchestrator anyway).

## 3. Whether `prro_crypto` already speaks CMP

**Yes — fully, including the HTTP client.** No M2 work on the wire
layer is required.

Evidence:
- Module: `rust/prro_crypto/src/cms/cmp.rs` (591 lines, complete).
- Public API:
  - `encode_iit_cert_lookup(ski: &[u8]) -> Result<Vec<u8>, CmpError>`
    (`cmp.rs:104-125`).
  - `parse_iit_cert_response(body: &[u8], expected_ski: &[u8]) ->
    Result<Vec<u8>, CmpError>` (`cmp.rs:133-174`).
  - `fetch_cert_by_ski(cmp_url: &str, ski: &[u8], timeout: Duration)
    -> Result<Vec<u8>, CmpError>` (`cmp.rs:311-349`) — combined
    encode + POST + parse round-trip, gated on
    `#[cfg(feature = "tsp_http")]`.
- Feature flag:
  `rust/prro_crypto/Cargo.toml:52` declares `default = ["tsp_http"]`
  and `tsp_http = ["dep:ureq"]` (`Cargo.toml:57`). Defaults are on, so
  the M2 `cert_refresher` consuming `prro_crypto = { path = "...",
  default-features = true }` (or any subset that re-enables
  `tsp_http`) gets the function.
- Error model: `CmpError` (`cmp.rs:63-89`) is already split into
  `Http(transport)` vs `HttpStatus { code, status_text }` vs
  `ServerError(u32)` vs `NotFound` vs structural parse errors. Maps
  cleanly onto a service-level retry policy — `cert_refresher` should
  retry on `Http` (5xx-ish), short-circuit on `HttpStatus` 4xx, treat
  `NotFound` as "leave the active cert in place, alarm via metrics".
- DoS hardening already done: 1 MiB body cap (`cmp.rs:344`), 32-deep
  ASN.1 recursion cap, 8192 TLV-visit cap (`cmp.rs:193-194`). The
  iterative walker (`cmp.rs:189-272`) is explicitly non-recursive —
  meaning the cert_refresher does not need to add its own DoS guard.

**What M2 *does* need to add (and what stays out):**

| Layer | Owner crate | M2 work? |
|---|---|---|
| Encode 120-byte IIT payload | `prro_crypto::cms::cmp` | NO — done |
| ASN.1 wrap/unwrap | `prro_crypto::cms::cmp` + `der_writer` | NO — done |
| Blocking HTTP POST | `prro_crypto::cms::cmp` (ureq) | NO — done |
| SKI re-check on response | `prro_crypto::cms::cmp` | NO — done |
| **Async wrapper**, retry, backoff, multi-URL fallback | `prro::services::cert_refresher` | **YES** |
| **DB upsert + atomic active-flip** | `prro::services::cert_refresher` (via repos) | **YES** |
| **Refresh schedule** (timer / tokio task) | `prro::services::cert_refresher` | **YES** |
| Audit log entry (`CERT_PROVISIONED`-equivalent) | `prro::services::cert_refresher` | **YES** |
| OCSP / CRL / TSP fetchers (parallel CSP services) | `prro_crypto::cms::revocation`, `tsp` | NO — out of scope of ADR-M2-4 |

The Python service today calls a *blocking* `fetch_cert_by_ski` from
inside its synchronous handler. In Rust, `cert_refresher` runs as a
background task — a candidate is to call the existing blocking
`prro_crypto::cms::cmp::fetch_cert_by_ski` via
`tokio::task::spawn_blocking` rather than introducing an async HTTP
client. (Rationale: keeps `prro_crypto` zero-async and avoids an
ureq → reqwest swap that would expand surface area and dependency
churn.) Final choice is W1+ implementation detail; this finding only
notes that no protocol work is needed.

## 4. Test-CA strategy

**Choice: vendored CA fixture (replay recorded responses), with a
small live-acskidd smoke test gated `#[ignore]`.**

### 4.1 Strategy detail

A test-only fixture under
`rust/prro/tests/fixtures/cmp_responses/` that holds:
- One success case: a real IIT response captured offline (from
  acskidd against the well-known DPS-own SKI, or from a
  developer-owned cert), stored as raw bytes in a `.bin` file plus a
  metadata `.json` (queried SKI, expected response status, expected
  cert fingerprint).
- One `not found` case: a synthesised IIT response with status=1 and
  an empty SignedData inner.
- One `server error` case: status=5 (matches existing
  `parse_rejects_non_success_status` test at `cmp.rs:399-414`).
- One `malformed body` case: deliberately truncated IIT payload.
- Optional: one `pathologically deep` case (mirrors
  `parse_rejects_pathologically_deep_response` at `cmp.rs:471-509`).

The integration test then spins a tiny in-process HTTP server
(simplest option: `wiremock` crate, or hand-rolled `tokio` listener
that reads the request body, looks up the matching response, and
writes it back). `cert_refresher` is pointed at
`http://127.0.0.1:<port>/services/cmp/` and exercised end-to-end:
- "fetch + persist + flip active" happy path
- "transport error → no DB write, alarm metric incremented"
- "cert not yet expired → no fetch attempted"
- "stage cert at active=0 then atomic-flip" (covers ADR-M2-4 atomic
  flip test requirement)
- "CMP returns wrong SKI → reject, alarm" (the parser already enforces
  this; test that the orchestrator surfaces it correctly)

### 4.2 Why this option

- **CI-runnable** — no live network dependency. (Acceptance criterion
  rules out hitting the production endpoint.)
- **Fast** — sub-second per scenario; `cert_refresher` integration
  tests will join the normal `cargo test` suite.
- **Stable** — IIT wire format has been stable for years per
  `dstucrypt/agent`'s git history; the chance of "schema drift"
  invalidating fixtures is genuinely low. The format doesn't even have
  a version negotiation byte beyond the `02 00 00 00` constant at
  offset 8.
- **Cheap to refresh** — a new fixture is `curl --data-binary @req.bin
  http://acskidd.gov.ua/services/cmp/ > resp.bin` plus a recorded
  metadata file. Documented as a one-liner alongside the fixture
  directory.
- **Covers the structural diversity** of responses the parser must
  handle (success / status-error / not-found / malformed / deep).

### 4.3 Alternatives rejected

**Self-hosted RFC-4210 stub (Rust or Python):**
- *Rejected because* — there is no RFC-4210 traffic on this channel.
  Building an RFC-4210 stub would test code that does not exist and
  fail to test the code that does (the IIT 120-byte format).
  Building an *IIT-stub* (separate option below) is closer.

**Self-hosted IIT-format stub (in-process Rust mock):**
- *Considered, partially adopted* — the recorded-fixture replay above
  IS such a stub, just driven by stored bytes rather than synthesised
  ones. A pure code-gen stub (encode the response from a cert in the
  test) is also viable and complementary. **Recommendation:** use the
  vendored fixture for "what the wire actually looks like" cases and
  synthesise responses on the fly for negative-path tests (status=5,
  pathological depth). This matches what `cmp.rs:399-509` already
  does at the unit level.

**Live operator-test endpoint (acskidd or uakey):**
- *Rejected for CI* — `acskidd.gov.ua:80` is a production CA front;
  pointing CI at it is unsafe (rate limits, accidental load, audit
  trail noise on the CA side). Project memory `DPS rate limit`
  documents that test endpoints already throttle errors hard.
- *Retained as `#[ignore]` smoke* — keep one live test in
  `rust/prro/tests/integration_cert_refresher_live.rs` (or similar),
  marked `#[ignore]`, that requires `cargo test -- --ignored` to run
  manually. Mirrors the existing pattern at
  `rust/prro_crypto/src/cms/cmp.rs:516,548,576`.

**Vendored capture without a server (test calls a function directly,
no HTTP loop):**
- *Rejected* because it would not exercise the `cert_refresher`'s
  retry / multi-URL / timeout logic, which is the *new* code being
  added in M2. The point of the integration test is to test that new
  orchestration, not to re-test the parser.

### 4.4 Concrete test-vector schema

A fixture directory layout:

```
rust/prro/tests/fixtures/cmp_responses/
  acskidd_dps_own_success/
    request.bin            # 120-byte payload + outer ContentInfo
    response.bin           # exact bytes returned by the CA
    meta.json              # { "ski_hex": "...", "expected_cert_fpr_sha256": "..." }
  not_found/
    response.bin           # synthesised: status=1, empty inner
    meta.json              # { "ski_hex": "<unknown>" }
  server_error_status_5/
    response.bin           # synthesised
    meta.json              # { "ski_hex": "...", "expected_error": "ServerError(5)" }
  malformed_truncated/
    response.bin
    meta.json              # { "expected_error": "Parse" }
```

Capture instructions for `acskidd_dps_own_success` (run manually,
network-side, not in CI):

```sh

# rust/prro_crypto/src/cms/cmp.rs:522-526 (DPS_OWN_SKI).
cargo run --example dump_cert -- \
    --cmp-url http://acskidd.gov.ua/services/cmp/ \
    --ski-hex 14EDC20697BD372393CA35A01E124E9EC0A2CA0139FB7FB2BC5C81C92E13B037 \
    --capture-out rust/prro/tests/fixtures/cmp_responses/acskidd_dps_own_success/
```

(The `dump_cert` example already exists at
`rust/prro_crypto/examples/dump_cert.rs` per repo top-level — extending
its CLI to dump the raw response in addition to the parsed cert is a
trivial M2 follow-up if it doesn't already.)

## 5. Boundary — `cert_refresher` (services::) vs `prro::crypto`

This section codifies the staged-pipeline rule of ADR-M2-6 against the
specific shape of the cert refresh path.

```
┌──────────────────────────────────────────────────────────────────────┐
│ prro::services::cert_refresher                  (ADR-M2-6 carve-out) │
│  - holds &SqlitePool                                                 │
│  - schedules refresh loop (refresh_within_days)                      │
│  - reads operator_certs rows due for refresh                         │
│      [stage 1: with_immediate, drop tx]                              │
│  - calls the CMP fetch primitive                                     │
│      [stage 2: NO tx, NO DB handle in scope]                         │
│  - persists fetched cert at active=0 + atomic flip                   │
│      [stage 3: with_immediate, single CAS UPDATE compound]           │
│  - emits audit log entry                                             │
│      [stage 3 same tx]                                               │
└──────────────────────────────────────────────────────────────────────┘
              │ stage 2 calls into ↓
┌──────────────────────────────────────────────────────────────────────┐
│ prro_crypto::cms::cmp                                                │
│  pub fn fetch_cert_by_ski(cmp_url: &str, ski: &[u8],                 │
│                           timeout: Duration)                         │
│      -> Result<Vec<u8>, CmpError>                                    │
│  - NO &SqlitePool / SqliteConnection / Pool<Sqlite> / Transaction    │
│    in signature (ADR-M2-6 conformant — already true today).          │
│  - NO `tracing` field that names a secret (none on this path).       │
│  - Pure (URL + SKI bytes + timeout) -> (cert DER bytes | typed err). │
└──────────────────────────────────────────────────────────────────────┘
```

**Decisions encoded above (each maps to ADR-M2-4 or ADR-M2-6):**

1. `cert_refresher` lives under `prro::services::` (or wherever M1
   places service modules — currently `rust/prro/src/{lib.rs, app.rs,
   db, runtime, config}` exists; `services::` is M2-new). It accepts
   a `SqlitePool` clone in its constructor. **ADR-M2-6 §320–330
   carve-out applies.**
2. `cert_refresher` MUST NOT hold a `SqliteConnection` /
   `Transaction` across the CMP fetch. The pattern is: open tx →
   read candidates → drop tx → fetch → open tx → flip active → drop
   tx. Mirrors Python at `services/cert_provisioning.py:412-415`
   (read-only candidates query) and `:554-587` (short
   `BEGIN IMMEDIATE` for upsert + audit).
3. `prro_crypto::cms::cmp::fetch_cert_by_ski` ALREADY conforms to
   ADR-M2-6: it takes `(&str, &[u8], Duration)` and returns
   `Result<Vec<u8>, CmpError>`. No DB handle. The CI lint required by
   ADR-M2-6 (§361–366) will verify this remains true.
4. The atomic flip is a single SQLite statement compound:
   `UPDATE operator_certs SET active = 0 WHERE fiscal_number = ? AND
   active = 1; UPDATE operator_certs SET active = 1 WHERE ski_hex =
   ?`. Both run inside the same `with_immediate`. The partial unique
   index `ux_op_certs_active_per_fn`
   (`rust/prro/migrations/003_operators_printers.sql:47-48`) enforces
   the invariant at the storage layer.
5. ADR-M2-5 secret-flow rules **do not apply** to `cert_refresher` —
   no plaintext key material, no JKS password, no `cred_salt` flow
   through this path. The pubkey extracted from the existing cert (to
   recompute SKI for queries) is public. The only sensitive output is
   `cert_der`, which is itself public.

**Implication for the CI lint planned in ADR-M2-6 §361–366:**

The lint, when implemented, scans `crypto::` and `transports::` only.
`services::cert_refresher` is exempt. `prro_crypto::cms::cmp` already
passes (no DB types in its public API). No additional surfaces need
exempting.

## 6. Deferred questions and the assumption that closes them

### 6.1 Deferred — but with closing assumption

| Question | Closing assumption (M2 W1+ may rely on this) |
|---|---|
| Does `cert_refresher` need *any* form of CA-side authentication for revocation events? | NO. Revocation is observable via OCSP/CRL (separate channel, `prro_crypto::cms::revocation`); CMP-style cert lookup does not gate on revocation. `cert_refresher` will stick to "fetch latest cert; if expired or revoked, alarm via metric and continue with stale cert until manual replacement". |
| Should `cert_refresher` support multiple CSPs (acskidd, uakey, privatbank, etc.) with priority routing? | YES — per `sql/016_ca_endpoints.sql` and `services/cert_provisioning.py:472-501`. M2 must port the multi-URL retry policy. The primary `cert_provisioning_config.primary_cmp_url` default `http://acskidd.gov.ua:80` is a *legacy fallback* superseded by `ca_endpoints` rows; treat it as last-resort. |
| Does the M2 schema need a new `ca_endpoints` table to mirror `sql/016`? | YES, but deferred to W1+. M1 schema (`003_operators_printers.sql`) already has `cert_provisioning_config` but does NOT yet have `ca_endpoints`. M2 can either add it or hardcode the priority list. **Recommendation**: add the table in M2 W1, mirroring `sql/016_ca_endpoints.sql` verbatim. (Not blocking this finding.) |
| Should `cert_refresher` use async HTTP (reqwest) or wrap the existing blocking `ureq` call in `spawn_blocking`? | `spawn_blocking` over the existing `prro_crypto::cms::cmp::fetch_cert_by_ski`. Rationale: keeps `prro_crypto` async-free; avoids dep churn; CMP fetches are infrequent (per-FN, every `refresh_within_days`) so blocking-thread cost is negligible. Final call deferred to W1+ implementer; this finding does not block on it. |
| What is the `cert_refresher` scheduling cadence (poll interval vs event-driven)? | Periodic poll, every `cache_ttl_seconds` (M1 default 3600). Mirrors Python `RuntimeContainer`-managed background loop (referenced at `services/cert_provisioning.py:33` "FI-9: refresh_expiring_certs is a loop body; the poller owner controls its stop-event"). The cadence parameter is already in the M1 schema (`003_operators_printers.sql:55`). |

### 6.2 Genuinely open (will require live network or operator-test creds)

| Question | Why deferred |
|---|---|
| Does acskidd return the *full chain* (end-entity + intermediates + root) on a single SKI lookup, or only the end-entity? | Determines whether `cert_refresher` needs a chain-walking pass or can persist the single returned cert directly. Current Rust code returns only the matching cert; the question is whether the response payload contains more that the iterative walker is dropping. **Closing assumption** for W1+: persist whatever `fetch_cert_by_ski` returns; if chain validation is needed, that's a follow-up sprint and uses OCSP/CRL routes already in `prro_crypto::cms::revocation`. |
| Does any Ukrainian CSP rate-limit the lookup endpoint (per IP, per day)? | Affects cadence sizing. **Closing assumption** for W1+: refresh cadence bounded by `cache_ttl_seconds` (default 3600) per FN; with N operators, worst case is N requests per hour to a single CA, which is well below any realistic rate limit. Cadence remains tunable via config. |

These two questions can be answered with two manual `curl` probes from
a dev box; the closing assumptions above are conservative enough that
M2 W1+ does not block on them.

## 7. ADR revision (optional, non-blocking — proposed diff only)

ADR-M2-4's "Open risk" paragraph (§230–234) currently says:

> "CMP protocol details (which endpoint, primary vs fallback URLs,
> authentication mode) are still spec-only. M2 plan must include a
> task to implement a thin `CmpClient` against the test CA before
> the cert_refresher integration test can run."

## Appendix A — Schema / config drift notes (informational)

Two minor drift items observed during the probe; neither blocks W1+.

1. **`primary_cmp_url` default has no path component.** Both the M1
   Rust schema (`rust/prro/migrations/003_operators_printers.sql:52`)
   and the Python model
   (`src/prro_gateway/models/storage.py:302`) default
   `primary_cmp_url` to `http://acskidd.gov.ua:80` (no
   `/services/cmp/`). The actual endpoint is
   `http://acskidd.gov.ua/services/cmp/`. The Python orchestrator
   never hits this default in practice because `ca_endpoints` rows
   (`sql/016_ca_endpoints.sql:30`) carry the full URL and are tried
   first. M2 W1+ could either:
   - patch the schema default in a follow-up migration, OR
   - drop the field entirely once `ca_endpoints` is mirrored on the
     Rust side.
   Recommend: drop the field in M2 W1+ schema cleanup. It is a legacy
   trap that will mislead anyone reading the M1 migration cold.

2. **`fallback_cmp_url` is unused.** The M1 schema defines it
   (`003_operators_printers.sql:53`) but neither the Python nor any
   Rust code path consults it; the multi-URL retry uses `ca_endpoints`
   instead. Drop on the same M2 W1+ schema cleanup.

These are noted for the M2 W1+ schema author. They are out of scope of
W0-2 itself.

## Appendix B — One-line summary for the M2 plan

`cert_refresher` (M2 W1+) is a thin async + DB orchestrator around
the already-complete `prro_crypto::cms::cmp::fetch_cert_by_ski`,
running on a periodic schedule, doing fetch outside any DB tx and
atomic active-flip inside a `with_immediate` tx. No CMP protocol
work. No auth handshake. Tests run against a vendored fixture replay
server, with one `#[ignore]`'d live smoke against acskidd retained
for manual verification.
