# M3-W0 research mini-plan — close 5 M3-entry decisions before write-path implementation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:subagent-driven-development (recommended) or superpowers-extended-cc:executing-plans to execute this plan task-by-task.

**Goal:** Close the 5 M3-entry decisions surfaced in `docs/M2-handoff.md` §4.3 by producing 3 frozen findings/spec documents. After this mini-plan, an ADR (or ADR amendments) + the M3a implementation plan can be drafted on solid ground without re-litigating state-machine, lock-discipline, or retry-policy questions inside implementation tasks.

**Why W0-first:** write-path is the highest-risk zone in this codebase (lnd, state transitions, retry/recovery, idempotency, shift/offline/node interactions). Five named decisions are open — guessing them in the implementation plan and then patching in code costs an order of magnitude more than nailing them in research now. M2 used the same W0 pattern (3 findings docs, ~3 days) and it kept the M2 implementation plan stable across 7 W-tasks; M3 has more state-machine surface and deserves the same upfront discipline.

**Scope envelope (what this mini-plan IS):**
- 3 research tasks producing 3 frozen `docs/superpowers/specs/2026-05-06-m3-w0-{1,2,3}-*.md` documents.
- Each task closes named entry-decisions from the handoff and from open M3 bd issues.
- One administrative Task 0 to file the M3 epic + cross-link bd issues, mirroring M2 W0 Task 0.

**Scope envelope (what this mini-plan is NOT):**
- Not the M3a implementation plan. That is a separate plan written AFTER this one closes.
- Not the M3b plan (offline + recovery + reconciliation). M3b is gated on M3a operational signal.
- Not an ADR. Findings may surface proposed ADRs; those are reported to the coordinator/user, not committed inside research tasks.
- Not code. No `rust/prro/**` edits in any W0 task.

**Tech context:**
- Existing Python implementation lives at `src/prro_gateway/services/write_path.py` (6-stage pipeline) and `src/prro_gateway/services/reconciliation.py` (recovery). Python is the **behavioural reference** for what M3 must reproduce; deviations are explicit decisions, not silent re-designs.
- Rust substrate from M2 (`prro::crypto`, `prro::transports::dps`, `prro::xml`, `services::cert_refresher`) is frozen per `docs/M2-handoff.md` §2.
- bd epic + follow-ups: PRRO_GATE-82j (M2 epic, closed). M3 epic to be created in Task 0.

### Task 2 (W0-2): Lock discipline findings — `2026-05-06-m3-w0-2-lock-discipline.md`

**Goal:** Produce a frozen findings document that defines (a) every transactional boundary in M3 write-path with `with_immediate` requirements, (b) the Rust `db::tx::with_immediate` helper contract (what it forbids, how — compile-time / runtime / convention), (c) the `transition_state` helper contract (call-site requirement vs helper-side hardening), and (d) the boundary patterns that keep network/crypto OUT of locks.

**Day budget:** 1-2 days.

**Research-addresses:** PRRO_GATE-k99 (transition_state lock discipline). Reinforces invariant #1 (no network/crypto inside SQLite write transactions). Bd-issue closure deferred to M3a implementation time.

**Blocked by:** Task 1 (W0-1) — needs the state-transition table to know what `transition_state` calls are wrapping.

**Files (research outputs):**
- Create: `docs/superpowers/specs/2026-05-06-m3-w0-2-lock-discipline.md`

**Acceptance Criteria:**
- [ ] **Python audit** — full enumeration of every `with_immediate` site in `src/prro_gateway/` (services + repositories + runtime). Per site: what it protects (FK rows touched), what's legitimately inside (state transition + write), what should NEVER appear inside (network/crypto/cmp/dps), evidence of any current drift.
- [ ] **Transactional-boundary table** — for each of the 5 M3a pipeline stages: which writes happen inside `with_immediate`, which read-onlys can use a regular pool acquire, where prevhash + finalize bookkeeping lives. Tied back to the W0-1 sequence diagram.
- [ ] **`db::tx::with_immediate` Rust helper contract** — decision: (a) compile-time enforcement via a wrapper type / closure `Send` bound, (b) runtime `debug_assert!` / panic on misuse inside the closure, (c) convention + W5-style static check, (d) hybrid. **Each option must be paired with a feasibility verdict: what is genuinely enforceable vs what is policy-only.** Specifically: a runtime `debug_assert!` cannot universally catch "foreign IO `await` inside the tx closure" (no observable signal at the point of `.await` for a generic `impl Future`); the spec must say so explicitly. Compile-time enforcement is feasible for `spawn_blocking` (returns a `JoinHandle` whose `await` is detectable in a closure type) but not for arbitrary `async fn` calls. Pros/cons + the actual enforceability of each option explicit.
- [ ] **`transition_state` helper contract** — decision: (a) call-site requirement (every caller MUST be inside `with_immediate`; enforced by review), (b) helper takes a tx argument and proves it (refuses to run outside a tx), (c) helper opens its own micro-tx and the caller passes only the FK + transition tuple. Pros/cons + implications for the 4 state machines from W0-1 explicit.
- [ ] **Crypto/network boundary patterns** — explicit pattern catalogue: where crypto/network output must be staged (computed before `with_immediate` opens; passed in by value), where they must be deferred (after `with_immediate` commits; e.g. DPS send happens AFTER state flips to `SIGNED` and lock releases). Tied to W2 cert_refresher precedent (`compute_fingerprint` hoisted above lock).
- [ ] **App::boot impact** — preview of how the chosen helper contracts interact with App::boot reconciliation (full audit deferred to W0-3, but lock-discipline implications named here).
- [ ] **Reviewer checklist** at end: what a reviewer must re-verify if the helper contract changes.

**Verify:** `test -f docs/superpowers/specs/2026-05-06-m3-w0-2-lock-discipline.md && grep -E 'with_immediate|transition_state|invariant #1' docs/superpowers/specs/2026-05-06-m3-w0-2-lock-discipline.md`

**Out-of-scope:** specific retry semantics (W0-3), implementation of the helper (M3a plan).

### Task 3 (W0-3): Retry/recovery findings — `2026-05-06-m3-w0-3-retry-recovery.md`

**Goal:** Produce a frozen findings document that defines (a) WebCheck-derived retry classes for DPS interactions, (b) the DPS error taxonomy → retry-policy mapping (extension of M2 W3 `DpsError` 8-variant enum), (c) the pending-state recovery rules covering all 7 pending Document states (`PREPARED`, `SIGNED`, `ENCRYPTED`, `SENT`, `KVT1`, `KVT2`, `ERROR_RETRYABLE`) plus explicit exclusion rules for `OFFLINE_LOCAL_ACK` (handed off to offline_sync_service), `REQUIRES_MANUAL_RECONCILIATION` (operator-driven), and the 3 terminal states (`ACK` / `REJECTED` / `CANCELLED`), (d) the App::boot reconciliation contract that fixes PRRO_GATE-ah8.

**Day budget:** 2-3 days (largest W0 task).

**Research-addresses:** PRRO_GATE-6bj (retry/recovery policy), PRRO_GATE-ah8 (App::boot upsert behaviour). Bd-issue closure deferred to M3a implementation time.

**Blocked by:** Task 1 (W0-1) — needs state-transition tables to define recovery rules per state.

**Files (research outputs):**
- Create: `docs/superpowers/specs/2026-05-06-m3-w0-3-retry-recovery.md`

**Acceptance Criteria:**
- [ ] **WebCheck retry-class audit** — from `docs/webcheck_reverse/` + Python reconciliation logic, extract: classes WebCheck retries (transient transport, transient DPS, recoverable state mismatch), classes WebCheck does NOT retry (terminal cert error, terminal DPS reject, signature failure). Each class with concrete WebCheck source-line evidence.
- [ ] **DPS error taxonomy → policy table** — every `DpsError` variant from M2 W3 per `rust/prro/src/transports/dps/error.rs:14` — the 8 real variants are `Transport(String)`, `Authorization(String)`, `Decode(String)`, `Server { code: i32, message: String }`, `NotFound`, `ServerFiscalIdMismatch { expected_id, actual_id }`, `QueryNotSupported(&'static str)`, `Internal(String)`. Each mapped to: retry policy (none / N attempts with backoff curve / fail-over to offline / terminal), max attempts, backoff curve (constant / exponential / capped exponential), dead-letter destination (DB column / archive table / log-only). For `Server { code, .. }` — sub-table by raw status enum value (e.g. `ERROR_NOT_OPEN_SHIFT`, `ERROR_BAD_HASH_PREV`) since those drive distinct routing decisions.
- [ ] **Pending-state recovery rules** — for each Document state in the **pending set per `rust/prro/src/db/repositories/fiscal_documents.rs:176`** — `PREPARED`, `SIGNED`, `ENCRYPTED`, `SENT`, `KVT1`, `KVT2`, `ERROR_RETRYABLE` (7 states; KVT2 is included to avoid the strand-between-KVT2-and-ACK scenario): exact App::boot reconciliation action (re-drive forward / re-query DPS / mark recoverable / mark stuck for operator). Plus **explicit exclusion rules** for `OFFLINE_LOCAL_ACK` (handed off to offline_sync_service worker), `REQUIRES_MANUAL_RECONCILIATION` (operator-driven), and the 3 terminal states `ACK` / `REJECTED` / `CANCELLED`. Tied to W0-1 state-machine table.
- [ ] **App::boot reconciliation contract** — closes PRRO_GATE-ah8: existing FN rows must NOT be blindly `upsert_initial`-ed; shift_state must be preserved; node state must be re-evaluated against persisted last-known state. Specific Python `boot()` call sites enumerated; specific Rust contract (precondition + postcondition) defined.
- [ ] **Offline failover trigger map** — for the subset of retry classes that fail over to offline (open offline session, route subsequent docs to offline pool until ONLINE recovers): explicit trigger conditions + node-state interaction. M3a does NOT implement offline writes, but the trigger contract must be defined here so M3a's "ONLINE only" carve-out is unambiguous.
- [ ] **Reconciliation deterministic-replay invariant** — recovery must produce the same final state regardless of crash-and-resume vs uninterrupted run. Explicit examples per pending state.
- [ ] **Reviewer checklist** at end.

**Verify:** `test -f docs/superpowers/specs/2026-05-06-m3-w0-3-retry-recovery.md && grep -E 'DpsError|App::boot|reconciliation' docs/superpowers/specs/2026-05-06-m3-w0-3-retry-recovery.md`
