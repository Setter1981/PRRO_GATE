# Maria 304 Driver — Virtual Fiscal Register TCP Emulator

> **For agentic workers:** Self-contained implementation plan.  Every
> protocol byte, command mapping, and business rule required to complete
> this project is reproduced here.  You do NOT need the Claude chat
> transcript that produced this plan.
>
> REQUIRED SUB-SKILL when implementing: `superpowers-extended-cc:executing-plans`.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a single Rust binary `maria304_driver` that exposes a TCP
endpoint which speaks the EKKR «Мария-304» wire protocol bit-exactly.
Accounting software (1C, BAS, POS terminals) that talks to the stock
**Resonance OLE Manager** DLL must be unable to distinguish our
endpoint from a real Maria 304 register.  Receipt/shift/report semantics
are forwarded via HTTP to the existing Python PRRO Gateway, which owns
canonical data, DPS submission, and archival.

**Why:**
- Customers with legacy 1C integrations expect a physical Maria 304 on a
  COM port or `tcp://host:port`.  Today migrating them means replacing
  the 1C module — expensive, slow, per-customer.
- Our virtual device is an ingress channel peer with REST/XML-RPC: same
  canonical model, same Python write-path, same DPS path.  1C stays
  unchanged.
- A single Rust binary per deployment hosts N listeners (one TCP port
  per `fiscal_number`), enforcing the Maria-specific exclusive-connection
  semantics and 3-second reconnect cooldown from the real hardware.

**Scope boundaries (explicit non-goals):**
- No printing — `maria304_driver` never drives a physical printer.  Print
  support is planned at PRRO-Gateway level later, independent of this
  driver.
- No RS-232 — TCP only.  Virtual COM bridges (`com0com`, `socat`) can be
  used by operators externally if needed.
- No fiscal-memory emulation, no КСЕФ (`XMLS`/`XMLX`) — those are
  stubbed to plausible responses.  Full KSEF replay lives elsewhere.
- Only X-report, Z-report, and periodic report (`FIRN`/`FIRP`/`IREN`/
  `IREP`) are fully implemented.  Analytical and service reports are
  stubbed to `DONE`.

### Process boundaries

- `maria304_driver` is a separate OS process from the Python gateway.
  They communicate via loopback HTTP (or any reachable network — see
  `bridge.gateway_url`).
- Rust owns wire-protocol correctness and session lifecycle.  Python owns
  canonical business logic, fiscal state, DPS submission, archival.
- No direct SQLite access from the Rust driver.  All reads/writes go
  through HTTP.

### Deployment topologies

- **Single-host (pilot):** both binaries on the cashier's Windows box.
  `bridge.gateway_url = "http://127.0.0.1:8000"`.  1C points at
  `tcp://127.0.0.1:9100`.
- **Centralised (fleet ≥5 cash registers):** Python gateway on a shop
  server, `maria304_driver` on the same server, 1C on each cashier
  station points at `tcp://shop-server:9100+N`.

## 2. Wire protocol reference

**Source of truth:** `docs/ekka/304T-1_protocol.pdf` (official EKKA
protocol reference, 67 pages) + byte-for-byte cross-check against
decompiled `Resonance.EKKR.Message.GetBytes` and
`Resonance.EKKR.Rs232Transport.try_extract_message`.

### 2.1 Frame format

Bidirectional; identical shape for VU→EKKR and EKKR→VU:

```
┌─────────┬──────────────────────────┬──────────────┬───────┬──────────────────┐
│  START  │  payload (CP866 bytes)   │  length byte │  END  │  CRC-16 LE (opt) │
│  0xFD   │  4..252 bytes            │  = len(p)+1  │  0xFE │  lo / hi         │
│ 1 byte  │                          │  1 byte      │ 1 byte│  2 bytes         │
└─────────┴──────────────────────────┴──────────────┴───────┴──────────────────┘
```

### 2.2 Invariants

| # | Rule |
|---|------|
| W1 | `0xFE` and `0xFF` **may not** appear inside the payload.  Encoder replaces them with `0x20` (space) — matches firmware. |
| W2 | `payload.len() ∈ [4, 252]`.  Length byte = `payload.len() + 1`, so its range is `[0x05, 0xFD]`. |
| W3 | CRC is optional until either party sends `CSIN1`.  After `CSIN1`, both directions must carry CRC. |
| W4 | CRC-16 is a **Maria-specific** polynomial.  Do NOT substitute CRC-16/CCITT — the shift order differs. |
| W5 | CRC is appended little-endian.  Self-verifying: `crc16(full_frame_including_crc_bytes) == 0`. |
| W6 | Encoding is CP866 with Ukrainian extensions: `і` 0xB9, `ї` 0xF5, `є` 0xF3, `ґ` 0xBB (+ uppercase).  Unknown glyph → `?` (0x3F). |
| W7 | Input strings must be Unicode NFC.  Decomposed forms are silently corrupted. |
| W8 | Reader must be streaming-safe.  TCP may deliver any partition; return `Incomplete` until a full frame arrives. |
| W9 | Frame buffer max size for a single decode attempt = `1 + 252 + 1 + 1 + 2 = 257` bytes.  Beyond that with no valid frame → stream is corrupt, caller must resync. |

### 2.3 CRC-16 algorithm

Hand-traced reference vector: `crc16("ABC") == 0x59E3`,
`crc16([0xFF]) == 0x0F78`.

```
crc = 0
for each byte b in data:
    crc ^= b
    a   = (crc ^ (crc << 4)) & 0x00FF
    crc = (crc >> 8) ^ (a << 8) ^ (a << 3) ^ (a >> 4)
return crc as u16
```

Rust implementation: `maria304_driver::wire::crc::crc16`.

### 2.4 LLV (Length-prefixed ASCII) encoding

Used inside composite commands (`PSDt`, `ACLD`, `CSHG`):

```
<2 ASCII decimal digits (00..99)>
<value bytes>
```

Examples:
- `""`   → `"00"`
- `"X"`  → `"01X"`
- `null` → `"00"`
- `"1234567890123456"` (16 chars) → `"161234567890123456"`

Max value length = 99 chars.  Longer → reject at construction.

Rust type: `maria304_driver::wire::Llv`.

### 2.5 Connection lifecycle

```
TCP ACCEPT
  │
  │  (No RS-232 U+U handshake in TCP path.  If the client sends 0x55
  │   probes anyway because it was written for virtual COM, reply with
  │   a single `READY` frame and ignore subsequent 0x55s.)
  │
  ▼
CONNECTED (CRC disabled)
  │
  │  Client → CSIN1       (enable CRC validation both directions)
  │  Server → DONE
  │  Client → SYNC        (confirmation ping)
  │  Server → DONE
  │  Client → UPAS<10-digit password><cashier_id>
  │  Server → DONE        (on valid password — default "1111111111")
  │
  ▼
AUTHENTICATED
  │
  ├─── queries (CONF, CONf, CCAS, CFIS, GLCN, ARTD, GETD) → always accepted
  ├─── setup  (HEAD, BOTM, CUTR, SVSL, ARMO, NALG, NPDI, NNAM, …) → stub DONE
  │
  ├── OpenCheck / OpenReturnCheck ──────►  RECEIPT_OPEN
  │                                          ├── FISC / BFIS / ARFI / ARBF / FICD / BFCD
  │                                          ├── GRBG / GREN
  │                                          ├── NLPR  (dual tax mode)
  │                                          ├── ACLD  (excise stamps)
  │                                          ├── PSDt  (acquirer slip)
  │                                          ├── AddPayment (accumulated client-side)
  │                                          │
  │                                          ├── COMP  → send canonical to Python
  │                                          │         → back to AUTHENTICATED
  │                                          │
  │                                          └── CANC+CTXT → back to AUTHENTICATED
  │
  ├── ZREP   → X-report via Python
  ├── NREP   → Z-report via Python (closes fiscal day)
  ├── nrep   → new shift, zero Z-report
  ├── FIRN / FIRP / IREN / IREP → periodic report
  │
  ▼
TCP CLOSE  (or graceful `Done()` from OLE Manager)
  │
  ├── Cleanup pending receipt: CANC + CTXT to server state
  │
  ▼
COOLDOWN (3 seconds — matches Maria hardware behaviour)
  │
  ▼
Listener ready to accept next connection for this FN
```

### 2.6 Exclusive-connection rule

Real Maria hardware accepts **exactly one** simultaneous connection.  The
virtual driver mirrors this: while a TCP session is active on a given
FN, a second `connect()` receives a `SOFTBLOCK` frame and is closed.

This matches the OLE Manager doc verbatim:
> "ЭККА одновременно может работать только с одним соединением"

### 3.5 Excise stamp batching

`AddExciseStamps(codes[])` batches stamp codes into one or more `ACLD`
frames.  Start with `"ACLD"`; append `LLV(code)` values until the frame
would exceed ~200 bytes, then flush and start a new `"ACLD"`.  Final
partial frame flushed at end.  Matches `fiscal_receipt.AddExciseStamps`.

## 4. COMP response format

The `COMP` response is the single most important wire frame — 1C
parses it to confirm the check was registered.

```
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│ segment 0│ segment 1│ segment 2│ segment 3│ segment 4│ segment 5│ segment 6│ segment 7│ segment 8│
│ 10 chars │ 10 chars │ 10 chars │ 10 chars │ 10 chars │ 10 chars │ 10 chars │ 10 chars │ 10 chars │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

Known (confirmed against 1C parser):
- **seg 0** `check_number` (ASCII-decimal, zero-padded)
- **seg 1** `sale_total` (копійки, D10)
- **seg 2** `return_total` (копійки, D10)

The remaining 6 segments are used for `Сумма_закрытого_чека` validation
inside the DLL but never surfaced to 1C.  Drivers can fill them with
derived values (e.g. VAT breakdown) or zeros — 1C does not read them.

Driver response construction:

```rust
format!(
    "COMP{check_no:010}{sale:010}{returns:010}{s3:010}{s4:010}{s5:010}{s6:010}{s7:010}{s8:010}",
    check_no = fiscal_id_from_python,
    sale = receipt.sale_total_kopecks,
    returns = receipt.return_total_kopecks,
    s3 = 0, s4 = 0, s5 = 0, s6 = 0, s7 = 0, s8 = 0,
)
```

```json

}
```

Driver maps `error_code` to the corresponding Maria wire error frame
(e.g. `SOFTBADART` becomes a response frame with that exact 10-char
text as payload).

## 8. Invariants (project-wide)

These mirror the CLAUDE.md frozen invariants that the driver must NOT
violate, plus driver-specific ones.

### 8.1 Inherited from PRRO Gateway

| # | Invariant | Driver impact |
|---|-----------|---------------|
| INV-1 | No network/crypto inside long SQLite tx | Driver has no SQLite at all |
| INV-2 | One fiscal_number = one logical single-writer | Enforced via per-FN TCP listener exclusion |
| INV-3 | Channel switch forbidden with open shift | Python validates; driver propagates error |
| INV-4 | Idempotency mandatory | `idempotency_key` sent with every bridge call |
| INV-5 | Offline must respect time/code limits | Python enforces |
| INV-6 | Adapters build full canonical payloads, not summary | `adapters/maria304_native.py` uses full canonical schema |
| INV-7 | All canonical envelopes carry `schema_version` | Bridge DTO includes it |
| INV-8 | Recovery must not silently violate state transitions | Driver retries via SOFTBLOCK; Python uses `expected_states` guards |
| INV-9 | Graceful shutdown > finishing fast | M9 drain policy |
| INV-10 | Signing bypass only by explicit config | Driver never signs; signing is Python's job |

### 8.2 Driver-specific

| # | Invariant |
|---|-----------|
| DRV-1 | No canonical business logic in Rust.  Receipt assembly = buffering only; validation happens in Python. |
| DRV-2 | Bridge contract is the stable boundary.  Wire protocol changes MUST NOT leak into bridge DTO semantics. |
| DRV-3 | One TCP connection per fiscal_number at any time.  Violating this risks duplicate check numbers. |
| DRV-4 | 3-second cooldown after TCP close is non-negotiable — OLE Manager assumes it. |
| DRV-5 | CP866 table is canonical.  Any glyph added to the table must also have a byte-level unit test. |
| DRV-6 | `SOFTBLOCK` is the driver's generic retry-me signal.  Permanent errors use specific `SOFT*` codes. |

## 9. Known unknowns

Items that require real-world capture or vendor confirmation before
they can be resolved with certainty.

1. **COMP segments 3–8 semantics** — known to be non-critical for 1C
   (tested), but exact meaning per the firmware is undocumented.  Fill
   with zeros for now; adjust if a captured integration exposes a
   consumer.

2. **Exact CP866 byte values for Ukrainian `°` and `·`** — mapped from
   IBM-866 extended table; not yet cross-checked against a real
   captured frame.  Unit test passes roundtrip but real-world byte
   may differ.

3. **`InitEx` signature variants** — 1C pilot code calls
   `InitEx(4, "Кассир", "1111111111", 0, "RBK", "localhost")` with 6
   arguments.  The DLL decompile shows 3 overloads with 4 parameters
   each.  Driver accepts any bytes before `UPAS` as
   vendor/dialect-specific and treats them as noise.

4. **`MDMD` settlement loop** — OLE calls `MDMD2301BB` in a tight loop
   after NREP until the response does NOT contain `MDMD420101`.  Our
   stub should respond with a payload that terminates this loop on
   first iteration (return `MDMD` with empty body or `MDMD2301BB`
   itself).  To be confirmed with real capture.

5. **Non-fiscal documents** (`DBEG`…`PRTX` with `TEXT` commands) —
   sometimes used for gift receipts / terminal slips.  Driver currently
   accepts them as stubs (DONE + echo).  If pilot needs real printing,
   deferred to post-M13 work.

6. **0x55 handshake probes via virtual COM** — if any customer uses
   `com0com`/`socat` to bridge COM to TCP, the DLL may send `U` bytes
   before any real command.  Our driver should ignore such prefix and
   emit a `READY` frame to keep the client happy.  To be exercised in
   M3 via integration test.
