## 0. Mission

Make the model-based differential fuzzer **maximally mean**: every production surface the gateway now has (or gains) must be predictable by the RefModel, checked by an INDEPENDENT oracle, and provably non-tautological (teeth). This dossier consolidates EVERY known uncovered surface into prioritized waves. Work wave-by-wave; each wave lands as its own reviewed increment (TEST-ONLY unless a wave explicitly says otherwise).

**Non-negotiable disciplines (apply to every wave):**
- **RED-first**: a new oracle/op lands with a failing pin first where feasible.
- **Teeth per oracle**: for EVERY new oracle, prove it bites — revert/break the guarded production invariant locally, watch the fuzzer go RED with clean shrinking, restore byte-exact. Record the teeth in the PR text.
- **Known-red fencing, never model-fudging**: an unresolved production question is EXCLUDED from the generator + fenced by an inverted-assertion known-red test (the `teeth_d5_shift_doc_superseded_known_red` pattern at `invariant_fuzzer.rs:333` — a test that FAILS if anyone silently normalizes the gap). No silent caps: anything excluded gets `log`ged in the PR + an issue.
- **TEST-ONLY**: production findings become ISSUES (like PRRO_GATE-eid), not drive-by prod edits. The only permitted production touches are additive `test-support` seams explicitly called out in W2; they must not change release behavior.
- **Determinism**: no wall-clock/randomness outside proptest; regression seeds committed (`invariant_fuzzer.regressions`, union-merge discipline).
- **Baseline preflight**: record the exact baseline SHA and prove that #251 + #252 and the semantic contents of the `9a7ad7c` drain-date fix (or its merged successor) are present. Test counts are evidence, not identity; do not start a wave on a similarly-green but older branch.
- **Oracle provenance**: every new assertion declares its independent source (`RefModel`, independent DB re-derivation, schema invariant, captured live-DPS/WebCheck bytes). An oracle MUST NOT compute expected values with the production helper it is checking.
- **Reachability + shrink fidelity**: every new generated op/edge ships with a deterministic emission/reachability pin. Keep the primary strategy flat and shrink-first (no `prop_filter`-heavy state machine); a green campaign in which the new arm was never reached is RED-equivalent.
- **Gate**: per wave — `cargo nextest run -p prro --features test-support --test invariant_fuzzer` green + the full crate gate + fmt + clippy, read from output.

## 3. WAVE 2 — the wire/envelope axis (the `-8` lesson)

1. **Envelope-format oracle.** The month-long `-8` hunt happened because NOTHING validated the wire ENVELOPE against the document class: our drain docs sent an epoch `date_time` where DPS requires the 14-digit `<TS>` integer (`kyiv_comp_date`, WebCheck parity, fixed in `9a7ad7c`). Teach a validating-DPS wrapper to assert an explicit matrix, not a vague "offline lane" rule: ordinary online SELL/RETURN/SHIFT_OPEN/Z → Kyiv-local-as-epoch; every offline-origin replay + BEGIN → 14-digit comp-date with non-empty `id_offline`; END → 14-digit comp-date BUT bare/empty `id_offline`; T=112 → its bundled 14-digit `comp_date`. Also pin `check_type`, `local_number`/`DI`, `id_cancel`, FN, and the signed `<TS>` equality. A violation must fail the harness directly with a typed assertion — do NOT synthesize a fake DPS status and then teach the model to accept it. **Teeth:** flip the `kyiv_comp_date` branch in `stage_send.rs` back to epoch for one doc-type → fuzzer REDs in one run.
2. **Validate the bytes that were actually signed.** The current deterministic crypto stub returns opaque constant CMS bytes, so `ScriptedDps` cannot honestly inspect `<TS>`/`<MAC>`. Add a fuzzer-only echo/attached-content signer or extract real attached `eContent`; the validator must parse the exact unsigned XML handed to crypto. It MUST NOT rebuild expected XML through the same production builder. If a seam is needed, keep it additive behind `test-support`; no production behavior change.
3. **XML-shape matrix per doc-type**: pin online and offline SELL/RETURN, SHIFT_OPEN, Z, BEGIN and END — including `<C T>`, `<Z NO>`, bare vs ID-bearing `<MAC>`, and that the hash covers the `ID` attribute. A drift in `emit_offline_session_boundary`, receipt builders, or Z-builder reddens without a live cabinet.
4. **Independent wire reference.** Add at least one captured live-accepted/WebCheck golden per envelope class and compare the raw prost `Check` fields (and, where stable, encoded bytes) with a small documented intentional-difference allowlist. The rule-validator catches internal inconsistency; the external golden catches a confidently-wrong rule-validator.

## 4. WAVE 3 — pool lifecycle + crash windows

1. **Pool ops + T=112 dual-tip model**: `Op::AskOfflineCodes(n)` is first-class — on ACK it atomically feeds the pool and advances the local chain to `sha256(request_xml)`; server reject changes neither. The ambiguous/lost-response branch is different: DPS MAY have issued codes and advanced its tip while local state remains unchanged. Model local and remote tips separately (or known-red fence the branch) so the next fiscal doc must recover, never silently fork.
2. **Retry ruling before generation (`PRRO_GATE-2ds`).** Fresh WebCheck v6.0.8.1368 sends T=112 through `SubmitPtr.SubmitCheck`, whose `All.Retries=18` loop retries status `0/-1`; current Rust `OfflineCodeReplenishService` deliberately pins transport error to one call/no retry because T=112 is non-idempotent. This is a real prod-vs-reference policy discrepancy. Keep the ambiguous T=112 retry sequence known-red until live/captured evidence decides: byte-identical resend, last-check probe, or no retry. Never encode the current implementation merely because it exists.
3. **Pool exhaustion + dynamic close reserve.** Do not freeze the oracle to magic `≤2`. Derive `required_codes_to_close = (BEGIN missing ? 1 : 0) + (offline Z missing ? 1 : 0)`; END is online-shaped and consumes zero. After every successful ordinary offline op with an open shift, assert `free_codes >= required_codes_to_close`. This refines the existing hard-reserve=1 rule for the lazy-BEGIN state and directly proves "a shift is NEVER wedged un-closable for lack of a code". Keep the operational refill watermark (`min_offline_codes`) separate from the legal close reserve.
4. **Crash windows**: generative `Crash(Sign)` buried-SIGNED (P1 follow-up), `Crash × Return` (R1 residual, pre-authorized), crash after T=112 remote ACK but before local persist, crash between the hoisted BEGIN and its business doc, crash between Z-quiescence and Z-send, crash mid-drain between content-ACK and END-mint. The #192 doc oracle is necessary but not sufficient: add a session-liveness oracle — at a quiescent boundary every `Draining` session has a durable next action or terminal/operator state, and bounded `Reboot/Drain` repetition converges (no empty-doc but permanently-Draining limbo).
5. **Idempotency width**: `DuplicateIdemKey` replays for shift/Z/T=112 trigger surfaces (today receipt-only). T=112 itself is not assumed idempotent; the trigger's durable request identity and the wire operation are separate contracts.

## 5. WAVE 4 — mode completeness + input hostility

1. **Node-mode alphabet**: `BLOCKED` / `STOP_MODE` / `CRYPTO_DEGRADED` entry ops + fail-closed behavior of every fiscal op in each mode (true-noop matrices, the closed-shift-matrix pattern). Refusal means no `fiscal_documents` row, no lnd/seed/code movement; audit/inbox effects follow their own persisted contract.
2. **DPS-channel switch is a separate op.** Node online/offline mode is NOT the frozen "channel switch" invariant. Add `Op::SwitchOutgressProfile(FSCO_ZZD|EVPZ_DPS)` and assert frozen invariant #3 / `LEGAL_INVARIANTS` INV-05: an open shift refuses the profile change with no durable routing mutation; a closed/quiescent FN may switch with an audit. Do not claim INV-05 coverage from NodeMode tests.
3. **Byzantine DPS has two harnesses** (input axis; backlog `byzantine_dps_handling`): (a) raw protobuf/CMS/XML decode fuzz below `DpsChannel`, because a typed `ScriptedDps<Result<CheckAck,...>>` has already bypassed decoding; (b) semantic adversary above decode for wrong-id ACKs, stale/newer tips, contradictory status/data, and unknown statuses. Oracles: never panic/unbounded-allocate, fail closed, no fiscal advance on unauthenticated/ill-shaped evidence, and no automatic offline flip from one hostile response. Teeth must break a real decoder/semantic guard, not only a stub branch.
4. **Receipt-input fuzz** (backlog `receipt_fuzz`): property-generate hostile canonical payloads (sum bounds incl. the known-red 50k cash-cap gap, tax-group edge rates, integer/rounding boundaries, bounded huge line/string counts) → invalid input never mints a fiscal row or moves lnd/seed/codes. Do not universally demand "pre-inbox": malformed adapter input may be pre-inbox, while a valid envelope with a fiscal validation failure may leave a terminal audited inbox row. Valid extremes round-trip the independent Z-aggregation oracle (banker's rounding at scale).

## 6. WAVE 5 — time axis (lands WITH the 168h/36h/24h increment)

The earlier "36h/shift" wording here was dimensionally wrong. The 2026-07-10 ruling also says **auto-Z unconditional**, while the May spec still says per-FN `shift_autoclose_enabled`. Before W5, land a short superseding policy note that explicitly resolves the toggle conflict; the fuzzer must not become the de-facto spec.

1. Add `Op::AdvanceClock(dur)` backed by ONE injected control-flow clock used by admission, offline accumulation, shift ticker, cert gate and boot reconciliation. Document business timestamps remain durable inputs; do not rewrite signed historical `<TS>` merely to advance the test clock.
2. Model all three boundaries from documents: 36h continuous-session, 168h calendar-month accumulator, 24h shift/auto-Z. Pin `threshold−1`, exact threshold, `threshold+1`, month rollover during an open offline session (168 resets; 36 does not), Kyiv DST/cutoff, backwards-clock input (no negative budget/fail-open), and reboot after each boundary.
3. Oracles: with enforcement ON, over-budget new fiscal ops refuse fail-closed while the legal close path remains reachable; regardless of the enforcement toggle, a shift never crosses the resolved shift limit without a durable Z attempt/outcome. Fence with known-red until the production increment and superseding policy both exist.
4. Include the 36h certificate-expiry SHIFT_OPEN gate / `KeyRotationPending` axis from the same clock seam; otherwise W5 does not cover the charter's advertised cert-window adversary.

## 7. WAVE 6 — fleet (Tier-3, pre-fleet phase)

Multi-FN concurrent interleaving: N independent FNs, interleaved op streams, per-FN single-writer isolation (INV-2) as the oracle (no cross-FN lnd/seed/pool/session/shift bleed). Split the proof into two lanes: deterministic correctness at N=2..4 with a controlled scheduler, and fleet soak/load at N=200. N=200 is NOT a substitute for forcing the two hard schedules: same-FN calls serialize, while different-FN calls demonstrably overlap (no accidental global mutex). Also pin same idempotency key on different FNs, crash/recovery of FN-A while FN-B progresses, fairness/no starvation, and shutdown with both held/waiting leases.

Recovery-class routing (`AutoOfflineFallback`, `TechSupportEscalation`, `KeyRotationPending`, `MacReseedRecovery`, `TechSupportRepair`) enters only when each class has a real production state/audit seam. Today part of that taxonomy is spec-only; phantom model enums would manufacture coverage. Fence absent classes known-red and link their production increments.

## 8. Cross-wave metamorphic oracles (add as soon as both paths exist)

1. **Online ≡ offline+drain** for the same business intent at final ACK: same fiscal semantics and Z contribution, with an explicit allowlist only for legitimate envelope/offline identifiers and timestamps.
2. **SELL + matching RETURN** has the predicted net Z/ledger effect under online, offline, crash and drain interleavings; derive the result independently from stored signed payloads.
3. **Drain chunking invariance**: one complete drain, many partial drains, and partial-drain+reboot converge to the same terminal ledger/session/shift/seed state.
4. **Replay invariance**: repeating an accepted idempotency key or recovery command does not mint another fiscal doc, consume another code, advance the seed, or duplicate the terminal outbox effect.
