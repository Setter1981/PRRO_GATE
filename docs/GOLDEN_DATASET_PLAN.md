**Дата:** 2026-04-14
**Статус:** Planned

---

## Мета

Витягти 500 реальних торгових операцій з WebCheck архіву, конвертувати в canonical формат PRRO_GATE, прогнати через наш pipeline на тестовому ДПС і підтвердити ACK.

---

## Принцип

**Не копіюємо XML WebCheck.** Беремо тільки сирі бізнес-дані з чеків:
- Назва товару (чистимо від `~` `` ` `` `~UKTZED~` `` ` `` `~` суфікса)
- Ціна (PRC)
- Кількість (Q)
- УКЗЕД (CZD)
- Акцизна марка (CA, якщо є)
- Податкова група (TX)
- Тип оплати

**Суму рахуємо самі** (price × quantity). Податки рахуємо самі. Все інше — наш pipeline.

### WebCheck DB структура

Таблиця `ksef`:
- `checkxml` — сирий XML чека (ФСКО формат `<RQ><DAT><C>...</C></DAT><MAC></MAC></RQ>`)
- `checksigned` — підписаний CMS payload
- `checkidficscal` — фіскальний номер від ДПС
- `DocType`: 0=SELL, 4=RETURN/SERVICE_OUT, 8=SHIFT_OPEN, 9=SERVICE_IN/OUT, 10=GO_ONLINE, 12=CASH_MOVEMENT, 80=Z_REPORT
- `sum` — сума (UAH з копійками, DECIMAL)
- `dt` — дата/час
- `offline` — 0/1/2

### Особливості формату WebCheck

- Суми в гривнях з копійками (SM="270.00"), у нас — в копійках (integer)
- Назва товару містить УКЗЕД: `"Пиво Карабас світле 0.5~` `` ` `` `~2 203 000 900~` `` ` `` `~"`
- WebCheck працював на старому протоколі частково — тому XML не копіюємо
- Є proprietary тег `<WebCheck>` — ігноруємо
- SERVICE_IN/OUT (DocType=9) — дані-заглушки ("mmmaaaccc"), непридатні
- Нові чеки (2026) мають `RM` (решта) та `<CA>` (акцизні марки)

## Артефакти

### 1. `scripts/webcheck_extractor.py`

**Вхід:** WebCheck SQLite DB path + параметри вибірки

**Логіка для кожного чека:**
1. Парсити XML → витягти `<P>` елементи
2. Для кожного товару:
   - `name` = NM без `~` `` ` `` `~...~` `` ` `` `~` суфікса
   - `price` = int(float(PRC) × 100) — UAH → копійки
   - `quantity` = int(float(Q) × 1000) — до міліграмів
   - `sum` = price × quantity / 1000 — **рахуємо самі, НЕ беремо SM з WebCheck**
   - `uktzed` = CZD (trim spaces)
   - `excise_mark` = CA attribute якщо є тег `<CA>`
   - `tax_id` = TX
3. Для оплат — беремо тільки тип (CASH/CARD), суму рахуємо як total_sum
4. `total_sum` = sum(goods[].sum) — **рахуємо самі**

**Вихід:** `golden/webcheck_500.jsonl` — по рядку на чек:

## Фаза 2: Multi-Protocol Proof

Той самий golden dataset прогоняється через всі три ingress-адаптери:

| Рівень | Ingress | Формат вхідних даних | Що доводить |
|--------|---------|---------------------|-------------|
| 1 | REST adapter | POST JSON | Canonical pipeline + DPS ACK |
| 2 | WebCheck XML-RPC adapter | XML-RPC call | XML-RPC нормалізація → canonical → ACK |
| 3 | Maria TCP adapter | Maria TCP протокол | Maria нормалізація → canonical → ACK |

**Один товар, ціна, кількість — три ingress шляхи — ідентичний результат.**

Це доводить:
- Адаптери нормалізують коректно
- Canonical модель працює незалежно від протоколу
- End-to-end proof всієї архітектури multi-protocol gateway на реальних даних

### Артефакт: `scripts/golden_multiprotocol_test.py`

- Читає `golden/webcheck_500.jsonl`
- Для кожного чека генерує 3 варіанти запиту (REST JSON, XML-RPC, Maria TCP)
- Відправляє через відповідний ingress
- Порівнює результати: document_state, server_fiscal_no мають співпадати
- Звіт: матриця протокол × результат
