# Testing Framework Roadmap — post-RAGE (synthesis 2026-07-10)

**Author:** architect. Synthesizes the "what else can improve the test framework" + "is it enough for confident development" discussion into a phased plan. **Sits AFTER the RAGE fuzzer waves** (`docs/FUZZER_TIER2_RAGE_DOSSIER.md`, W1-W6) in priority; the two are complementary.

## 0. Framing — three distinct things

- **RAGE waves (W1-W6)** = COVERAGE expansion — *what* is fuzzed (alphabet + oracles). Contracted, runs first.
- **This doc, §1** = framework METHODOLOGY — *how mean and how honest* the framework is. Runs after RAGE (cheap items may interleave).
- **This doc, §2** = confidence pieces that NO test framework provides — standing tracks, gate the pilot/fleet not the core.
- `docs/QUALITY_CHARTER.md` is the philosophy; this is the concrete build-out. The standing rule «every feature → check the fuzzer» ([[feedback_fuzzer_tracks_features]]) governs all of it.

## 1. Framework methodology improvements (prioritized)

**North Star (review round 2): deterministic simulation testing.** FW-3 (interleaving exploration), FW-4 (fault injection), and the T3 injected clock are steps toward ONE goal — the TigerBeetle/FoundationDB posture where time, I/O faults, and scheduling are all seed-driven and any failure reproduces from a single seed. Build each piece with a SHARED seed-plumbing convention (one campaign seed → clock + fault schedule + proptest case) so they compose into a simulator instead of three incompatible knobs.

### Tier 1 — biggest moat per effort
- **FW-1 · Mutation testing (`cargo-mutants`).** Automates + QUANTIFIES teeth across ALL production code: inject thousands of mutations (`<`→`<=`, branch deletion, `+`→`-`), measure the kill-rate; the SURVIVORS are an exact map of oracle-coverage holes. Turns "fuzzer-proven correctness" from a slogan into a tracked metric (charter ratchet). **⚠️ Consider pulling this FORWARD (before/alongside RAGE):** it measures the fuzzer ITSELF, so it directs the RAGE waves at real blind spots instead of guesses. Cheap to stand up (non-required CI job + a baseline run + a survivor triage list feeding RAGE priorities). **Scoping (round 2):** full-crate runs take hours — run INCREMENTAL on the PR diff (changed functions only) per-PR, FULL sweep scoped to the hot-zones (`write_path`, `reconciliation`, `transports`, repositories) nightly/weekly; otherwise it will be stood up once and abandoned.
- **FW-2 · Golden wire-corpus oracle.** The differential proves `code ≡ our-model-of-DPS`, NOT `code ≡ DPS` — exactly where `-8` lived for a month. A growing corpus of CAPTURED real DPS/WebCheck wire bytes, replayed by every envelope/decode test, closes the model↔reality gap structurally. Elevates the W2/W4 golden mentions into a standing capture harness (`golden/` + a differential against it). This is the WebCheck-differential-harness backlog, promoted to framework. **PII discipline (round 2):** promoted captures contain REAL receipts (ИНН, purchase lines — personal data). A sanitization step (deterministic anonymization that preserves wire shape/lengths/checksum-relevant fields) is MANDATORY before a capture enters the repo; unsanitized corpus in git is a legal defect, not a convenience.
- **FW-3 · Deterministic concurrency exploration (`loom` / `madsim`) for INV-2.** Single-writer-per-`fiscal_number` is the one large invariant tested by HOPE, not exhaustive interleaving. RAGE W6 runs an N=200 soak (statistical), which cannot PROVE no race. `loom` on the lease/single-writer path explores ALL interleavings — catches a race a soak misses.

### Tier 1b — pre-pilot obligations (added by the round-2 best-practices review; these gate the PILOT, cheap-to-medium each)
- **FW-12 · Migration/upgrade harness — the biggest omission of round 1.** Fleet reality: the riskiest moment for 200 cash registers is the UPDATE, and `migrations/` is already a named hot-zone — yet nothing tests it as a lifecycle. Build: (a) a library of durable-DB fixtures at EVERY released schema version (plus generated "aged" DBs: long audit logs, open shifts, mid-drain sessions, RMR states); (b) upgrade = run migrations on each fixture → `invariant_scan` + the fuzzer harness ON TOP of the migrated DB (not just "migrations apply"); (c) an explicit rollback/downgrade story test (at minimum: new binary refuses too-new schema cleanly, backup-restore path proven); (d) mid-migration crash (kill between steps) → boot recovers or refuses cleanly, never half-migrated-silent. Postgres/pg_upgrade and embedded-fleet A/B practice, adapted to SQLite.
- **FW-13 · Security & privacy test axis — absent from round 1.** (a) **Secret-leak pins**: logs/audit/error-messages/panics NEVER contain key material, JKS passwords, or full card-adjacent data — a grep-style harness over all emitted text surfaces under a full fuzzer run (the class is real: the JKS password already leaked into shell env once); (b) **supply-chain gate**: `cargo audit`/`cargo deny` job is currently RED and non-required — triage the 3 RUSTSEC advisories, then make it required-or-tracked; (c) ingress malformed-input fuzz (already CT-2/W4) explicitly includes auth/session surfaces when they appear. NOT in scope here: pen-testing the DPS side (not ours).
- **FW-14 · Prod-OS (Windows) test matrix.** The pilot's printing is Windows-only ⇒ the pilot PROD OS is Windows — but tests execute ONLY on linux-gnu (the msvc cross-nightly COMPILES, it does not RUN). SQLite locking, file semantics, path handling, and process-kill behavior all differ on Windows; the durability surface is untested on the OS it will run on. Minimum: a nightly windows-runner job executing the hot-zone suites (write_path, offline, drain, migrations, backup/restore) + the invariant fuzzer; crash/locking-sensitive tests prioritized.
- **FW-15 · Clock-skew adversary.** Register clock vs DPS clock drift is a certainty on a fleet (no NTP guarantee), and the whole `-8`/date class is time-sensitive. Test: local clock skewed ±N minutes from the DPS stub's notion of time → the system degrades PREDICTABLY (typed refusals / skew alert), never silent fiscal corruption; pins for the boundary where DPS would start rejecting our `<TS>`. Pairs with the T3 injected clock and RAGE W5 (`AdvanceClock`); a skew-sanity check (compare local clock to DPS-returned time, alert on drift) is the matching small PROD feature to file.
- **FW-16 · Invariant traceability matrix.** `LEGAL_INVARIANTS.md` INV-01..20 exist, but no map says WHICH pins/oracles hold each one. Maintain (ideally generate — tag tests with `// INV-xx` and grep) a matrix `invariant → tests/oracles/teeth`. Near-zero cost, and for an edge-fiscal product it is a SELLABLE compliance artifact (the moat, documented) + it exposes any invariant that is documented-but-unpinned.

### Tier 2
- **FW-4 · Physical fault injection.** Crash ops model LOGICAL windows only; SQLite errors, disk-full, partial writes, kill-at-syscall (fsync) — the durability PHYSICAL axis — are untested. **Concretized (round 2): do this at the SQLite VFS level** (the approach SQLite's own test harness uses — a shim VFS injecting write/sync/lock faults at chosen points), because that is exactly OUR durability surface (WAL + migrations + multi-step tx); a generic syscall killer is blunter and flakier. WAL-specific scenarios (crash mid-checkpoint, crash between WAL append and commit) are first-class cases. Feed the fault schedule from the shared simulation seed (North Star).
- **FW-5 · Real-crypto test lane** wired into the fuzzer/harness — signing is mocked (opaque CMS), so envelope/XML oracles cannot validate against genuine CMS. (`prro_crypto` vectors exist but aren't wired into the differential harness; W2-2 touches this — generalize it.)
- **FW-6 · Flakiness hunter** — a CI job running the suite ×N to surface nondeterminism systematically (the TMPDIR flake was found by accident).
- **FW-7 · Hot-zone coverage as a tracked (NOT gate) metric** (`llvm-cov`) — visibility into what's unexercised in `write_path`/`reconciliation`/`transports`; risk-weighted, ratchet-tracked.

### Tier 3 — heavier / longer
- **FW-8 · State machine as single source of truth.** Encode the 9-state shift / offline-session / doc / node machines as a DATA transition table; generate BOTH the fuzzer model AND a runtime "no illegal transition ever occurs" assertion from the SAME table — kills prose/dup drift. **Round 2: generate the AUDIT CONTRACT from the same table** — every transition maps to a documented audit event; a contract test asserts each fired transition emitted its event. The audit log is a LEGAL artifact; its completeness deserves a generated test, not convention.
- **FW-9 · Formal design check (TLA+ / Alloy)** of the shift/offline machine — checks the DESIGN (not the code) for deadlock / unreachable-terminal. Would have caught the superseded-unbounded-hold (PRRO_GATE-eid) at DESIGN time, before code. "Prove the core," not "test it."
- **FW-10 · Operational soak/chaos of the REAL binary** — start the gateway, drive traffic, `kill -9`, restart, assert recovery. Today recovery is unit/integration-tested, not "the actual binary falls and gets up." **Round 2: the soak MUST assert RESOURCE BOUNDS** — WAL file size stays bounded (checkpoint starvation is a classic SQLite production incident), fd count flat, RSS flat, audit/db growth linear-in-work — otherwise a leaking soak "passes" while dying slowly.
- **FW-11 · Perf-regression (`criterion`)** on the hot write-path — a latency regression is an operational risk (RTT budgets) that nothing currently guards. **Round 2: include DEGRADED-mode latency** — receipt p99 while DPS is slow/timing-out (backpressure behavior), not just happy-path throughput; the fiscal UX constraint is "the customer is standing at the till."

## 2. Beyond ANY test framework — standing confidence tracks (NOT one-time; gate pilot/fleet, not the core)

- **CT-1 · Live production feedback loop.** The ultimate oracle is reality. The live-DPS campaign (replay + diff + soak) must be ONGOING, not one-shot; real incidents feed the golden corpus (FW-2) and become permanent regression seeds. Tests cannot predict what the first real fleet deployment teaches.
- **CT-2 · Non-core surface coverage as the product grows.** The framework above is CORE-shaped. Ingress adapters (REST/XML-RPC/Maria — malformed-input fuzz), the sidecar-crypto prod path (vs passthrough), provisioning, env-isolation (demo/prod DB), monitoring, licensing, printing — each new surface (esp. the control-plane/fleet features from [[project_product_vision]]) needs its OWN harness under the «feature → fuzzer-check» discipline.
- **CT-3 · Operational safety net.** Staged rollout, monitoring, FAST rollback, human-readable RMR/audit dashboards, incident→test loop. Testing lowers risk BEFORE merge; deployment discipline manages the residual AFTER. A mean fuzzer whose failures no one can triage is half-useful.

## 3. Calibration — the honest bottom line

- **Fiscal-core correctness:** §1 makes risk **known, measured, and managed** — a rare, best-in-market level. **Enough to develop the core with high confidence.**
- **Pilot launch:** §1 **+ CT-1 + CT-3** (staged rollout / monitoring / rollback) **+ Tier 1b (FW-12 migration harness, FW-13 security/privacy, FW-14 Windows matrix — round 2)**. Tests do not replace a cautious first deployment.
- **Fleet scale:** core framework ready; every control-plane feature brings its own surface under the same standing discipline (CT-2).
- **There is no zero-risk** for an edge fiscal system with legal exposure. «Known + managed + measured + improving» IS the definition of confidence here — anyone promising zero is lying.

## 4. Sequencing recommendation (round 2)

1. **FW-1 (mutation, incremental-scoped) — pull forward, alongside RAGE** (it measures + directs the waves; cheap). **FW-16 (traceability matrix) — also now** (near-zero cost, compounding value).
2. RAGE W1-W6 (per the RAGE dossier) — the coverage backbone.
3. **FW-2 (golden corpus, with PII sanitization)** pairs with RAGE W2; **FW-3 (loom)** pairs with RAGE W6; **FW-15 (clock-skew)** pairs with RAGE W5 / T3's clock seam.
4. **Tier 1b before the PILOT:** FW-12 (migration harness), FW-13 (security/privacy axis), FW-14 (Windows matrix) — these gate the pilot, not the core.
5. FW-4..FW-7 (tier 2) as the campaign approaches.
5. FW-8..FW-11 (tier 3) as ongoing hardening; FW-9 (formal) is a high-value one-off for the shift machine specifically.
6. **CT-1 / CT-3 gate the PILOT**, not the core; **CT-2 is continuous** with product growth.

Confidence is a standing lock-step (alphabet-tracks-surface), not a finish line — this roadmap is infrastructure; the confidence comes from keeping it forever in step with the product.
